# 配置中心的设计与使用

## 配置模型

配置中心按「命名空间、分组、数据 ID」组织配置：命名空间隔离不同环境或租户，分组按业务模块划分，数据 ID 对应一份具体配置。同一份配置可以有多个版本，发布时生成新版本并记录操作人，回滚就是把生效版本指回历史版本，而不是手工改内容。

配置内容建议使用结构化格式（YAML 或 JSON），并做 schema 校验，避免把错别字或类型错误发布到线上。敏感配置（数据库密码、密钥）要单独加密存储，读取时按权限解密，不要和普通配置混在同一个明文文件里。

## 推送与监听

配置变更后要尽快通知客户端刷新。长轮询是常见实现：客户端带着当前版本发起请求，服务端在没有变更时挂起连接，超时或有变更时返回，客户端立即再发起下一轮。相比固定间隔轮询，长轮询能在保证实时性的同时减少无效请求。

客户端收到变更后要本地缓存并原子替换配置对象，避免读到半更新的状态。对关键配置还要支持「灰度推送」：先推给少量实例，观察错误率和日志，再全量推送；推送失败要能自动回滚到上一个版本。

## 配置使用的纪律

配置中心不是万能开关。代码里的分支逻辑如果完全依赖配置，会形成难以追踪的隐式行为；建议只把环境差异、限流阈值、功能开关这类真正需要动态调整的项放进去。每个配置项要有负责人、说明和默认值，默认值必须保证配置中心不可用时服务仍能启动。

启动阶段如果拉取配置失败，应使用本地快照降级启动，并持续重试，而不是直接崩溃；否则配置中心的一次抖动会放大为大规模重启。配置变更要有审计日志，能回答「谁在什么时候改了哪个值」。
