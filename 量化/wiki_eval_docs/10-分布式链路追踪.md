# 分布式链路追踪

## Trace 与 Span 模型

一次外部请求对应一个 Trace，Trace 内按调用层次拆成多个 Span：入口 Span 是网关或 Web 框架接收请求，子 Span 依次覆盖 RPC 调用、数据库查询、缓存访问和消息发送。每个 Span 记录开始时间、耗时、标签（服务名、接口、状态码）和事件日志。父子关系通过 Span ID 和 Parent Span ID 表达，形成一棵调用树。

Trace ID 要在进程边界传递。HTTP 场景放在请求头（如 traceparent），RPC 场景放在协议附带的 metadata 中，消息队列场景写入消息头。任何一次透传遗漏都会把一条链路截断成两段，所以框架层要统一注入和提取，而不是让业务代码手工传递。

## 采样策略

全量采集的成本很高，生产环境通常采样。固定比例采样实现简单，但低流量接口可能几乎没有样本；尾部采样在请求结束后根据耗时和错误决定是否保留，能优先保留慢请求和失败请求，代价是需要先把数据缓存在本地。

采样决策要在链路入口做一次并全程继承，否则同一 Trace 内有的服务采、有的不采，链路会不完整。对重点接口可以单独提高采样率或强制采样，但要有总量上限，避免大促时采集系统被打爆。

## 落地要点

埋点要覆盖框架层和中间件层，尽量自动化：Web 拦截器创建入口 Span，HTTP 客户端和 RPC 客户端创建子 Span，数据库驱动记录 SQL 耗时。业务自定义 Span 只加在关键步骤上，标签基数要控制，不要把用户 ID、完整 URL 参数这类高基数字段放进标签。

链路数据要和日志、指标关联：日志里打印 Trace ID，指标按服务和方法聚合。排障时先看指标定位异常服务，再用 Trace ID 找到具体调用链，最后跳到对应日志，形成闭环。
