# 消息幂等与顺序消费

## 为什么会重复消费

消息队列通常保证 at-least-once：消费者处理完业务但未来得及提交确认就宕机，消息会被重新投递；网络超时导致生产者重发，也会产生重复消息。因此消费者必须假设同一条消息可能到达多次，把业务处理设计成幂等。

幂等的常见实现是唯一键去重：用业务单号或消息 ID 建唯一索引，插入成功才继续处理，捕获唯一键冲突则直接确认消息。高并发下还可以先在 Redis 用 `SET key NX` 做短周期去重，再由数据库唯一索引兜底，避免所有请求都打到数据库。

## 幂等表与状态机

去重表要设置合理的保留期，不能无限增长；过期后同一消息再次到达仍可能重复处理，因此保留期要覆盖消息的最大重投窗口。另一种做法是状态机幂等：只允许订单从「待支付」流转到「已支付」，重复的支付消息因为状态已变更而被忽略，天然幂等。

幂等判断和业务写入必须在同一个事务里，否则可能出现「去重记录已写、业务失败」或「业务已写、去重记录丢失」的不一致。跨库场景要用本地消息表或事务消息来保证两者最终一致。

## 顺序消费的边界

全局顺序代价极高，通常只保证分区内或队列内顺序。生产者按业务键（如订单号）做哈希路由，把同一订单的消息固定到同一分区；消费者对分区单线程消费，或按业务键分发到内存队列后由单 worker 串行处理。

要注意顺序与重试的冲突：一条消息处理失败后如果跳过，后续消息会造成状态错乱；如果阻塞重试，又会拖住整个分区。工程上一般把无法处理的消息转入死信队列人工介入，并保证同一业务键的后续消息在该消息解决前不继续消费。扩分区会改变哈希映射，导致顺序在多分区迁移期间失效，扩容应选择低峰并暂停相关消费。
