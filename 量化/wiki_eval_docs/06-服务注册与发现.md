# 服务注册与发现（Consul）

## 注册与健康检查

服务实例启动后向 Consul 注册自身信息：服务名、IP、端口、标签和健康检查方式。健康检查支持 HTTP、TCP、gRPC 和脚本四种：HTTP 检查适合有健康端点的 Web 服务，TCP 检查只确认端口可连，脚本检查可以执行自定义逻辑。检查间隔和超时时间要匹配服务特点，间隔过短会带来额外压力，过长则故障发现不及时。

Consul 会把连续失败超过阈值的实例标记为 critical，并从健康的服务列表中摘除；实例恢复后自动重新加入。关键点在于健康检查必须反映「能否处理真实流量」，只检查进程存活会让流量继续打到已经无法服务数据库的实例。

## DNS 与 HTTP 接口两种发现方式

Consul 提供 DNS 接口和 HTTP 接口。DNS 方式对应用透明，服务通过 `服务名.service.consul` 解析到健康实例的 IP 列表，适合已有 DNS 解析能力的客户端；但 DNS 有缓存，实例变更后生效有延迟，TTL 要设置得足够短。HTTP 接口通过 `/v1/health/service/<name>?passing` 直接获取健康实例，信息更新更及时，还能读取标签和元数据做灰度路由。

客户端通常要自己做实例列表缓存和负载均衡。缓存要设置过期时间并支持后台刷新，避免 Consul 短暂不可用时服务调用全部失败。

## KV 与多数据中心

Consul 的 KV 存储适合存放少量动态配置和开关，例如限流阈值、灰度名单。KV 变更可以通过阻塞查询（blocking query）或 watch 机制推送给客户端，实现配置热更新。不要用 KV 存放大对象或高频写入的数据，它的定位是轻量元数据。

多数据中心通过 WAN gossip 互联，每个数据中心有独立的 server 集群，跨中心的服务发现通过 `服务名.service.<dc>.consul` 指定数据中心。跨中心调用要结合就近路由和故障转移策略，默认不要跨中心轮询，否则一次中心故障会放大成全站延迟。
