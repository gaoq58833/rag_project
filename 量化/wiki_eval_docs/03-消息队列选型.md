# 消息队列选型：Kafka、RabbitMQ 与 RocketMQ

## Kafka 的定位

Kafka 以分区日志为核心抽象，消息按分区顺序追加，消费者按 offset 拉取。它的吞吐高、可回放，适合日志采集、埋点、流式计算这类「量大、可重复消费」的场景。Kafka 不擅长单条消息的延迟投递和复杂路由，也不提供原生的延迟队列；需要延迟能力时通常靠外部调度或多级 topic 转发实现。

Kafka 的可靠性依赖副本机制：分区有 leader 和 follower，生产者通过 acks 控制确认级别，消费者提交 offset 决定重复消费的边界。acks=all 配合 min.insync.replicas 能避免 leader 宕机丢消息，但会增加写入延迟。

## RabbitMQ 的定位

RabbitMQ 基于 AMQP，强调灵活路由：交换机按 direct、topic、fanout、headers 把消息分发到队列，支持优先级队列、死信队列、延迟插件。它适合业务解耦、任务分发、对单条消息延迟和路由规则要求高的场景。吞吐量低于 Kafka，堆积大量消息时性能下降明显。

RabbitMQ 的确认机制分生产者 confirm 和消费者 ack。消费者处理失败可以 nack 并重新入队，但要注意重试风暴：无限重入会把队列打满，通常配合死信队列限制重试次数。

## RocketMQ 的定位

RocketMQ 在阿里内部大规模使用，提供事务消息、顺序消息、延迟消息等级别。事务消息用半消息加回查解决「本地事务与发消息」的原子性；顺序消息把同一业务键路由到同一队列，由消费者单线程消费保证顺序。它适合电商交易、订单状态流转这类既要求可靠又要求业务语义的场景。

选型时先看语义需求：需要回放和流处理优先 Kafka；需要复杂路由和低延迟任务优先 RabbitMQ；需要事务消息、延迟消息和顺序消息且团队接受运维成本，可选 RocketMQ。再看运维能力，任何 MQ 都要配套监控堆积量、消费延迟和死信数量。
