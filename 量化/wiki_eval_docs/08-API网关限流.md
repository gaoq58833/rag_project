# API 网关限流策略

## 常见限流算法

计数器算法按固定时间窗口统计请求数，实现简单，但窗口边界会出现双倍突发：窗口末尾和下一个窗口开头各放行一批，瞬时流量可能达到限额的两倍。滑动窗口把大窗口拆成多个小格，按时间滑动统计，边界问题明显缓解，代价是需要保存更多计数状态。

令牌桶按固定速率往桶里放令牌，请求取到令牌才放行，桶容量决定允许的突发量；漏桶则以固定速率流出，超出部分排队或拒绝，输出更平滑。对外 API 常用令牌桶，既能限制平均速率，又能容忍短时突发；对下游脆弱系统则更适合漏桶，把流量削平。

## 分布式限流

单机限流只能限制单个实例，实例扩容后总额限会成倍放大。网关层做全局限流时，计数要放在共享存储：Redis 的 Lua 脚本可以原子地完成「取当前计数、判断、加一、设置过期」，避免并发下的超发。热点 key 会集中在单个 Redis 分片，可以通过按 key 哈希分桶或本地预取令牌来分散压力。

限流维度要结合业务：按 IP 防止单用户刷接口，按 API 路径保护特定后端，按租户保证多租户公平。多个维度可以组合，但要有明确的优先级，避免规则互相覆盖导致实际限额与预期不符。

## 限流后的体验

被限流的请求要返回明确的状态码（429）和重试提示，并带上限流维度和剩余配额，方便客户端退避。直接断开连接会让客户端误以为是网络故障而立即重试，反而加剧拥塞。

对核心业务可以准备排队或降级方案：非关键请求直接拒绝，关键请求进入等待队列并给出预计等待时间。限流阈值不能拍脑袋，要基于压测得到的下游容量，再留出安全余量，并随容量变化定期复核。
