# Redis 分布式锁的实现与坑

## 加锁与释放的正确写法

分布式锁的第一要求是互斥。Redis 侧通常用 `SET key value NX PX ttl` 一条命令完成「不存在才写入」并同时设置过期时间，避免先 `SETNX` 再 `EXPIRE` 的两步操作在第二步失败时留下永不过期的锁。value 不能是固定字符串，而要放一个本次请求独有的随机值（如 UUID），释放时用 Lua 脚本先比较 value 再删除，保证「判断归属」和「删除」原子执行，防止 A 的锁过期后被 B 拿到、A 却把 B 的锁删掉。

锁的过期时间要大于业务最长执行时间的估计值，同时不能过大，否则持锁进程崩溃后其他请求要等很久。工程上一般把 TTL 设为业务 P99 耗时的 3 倍左右，并配合续期机制兜底。

## 续期与看门狗

业务耗时不可控时，需要给锁续期。常见做法是启动一个后台线程，每隔 TTL 的三分之一检查一次锁是否仍属于自己，如果属于就重置过期时间；业务结束后停止续期并主动释放。续期线程必须只在持锁期间运行，否则会在锁已被别人持有时不断刷新别人的锁。

续期也有边界：如果持锁进程发生长时间 STW（如 Full GC）或网络分区，续期可能中断，锁仍会过期，此时两个进程可能同时认为自己持锁。因此分布式锁只能降低并发冲突，不能替代数据库唯一约束这类最终防线。

## Redlock 的争议与替代方案

Redlock 的做法是向 N 个相互独立的 Redis 主节点依次加锁，超过半数成功且总耗时小于 TTL 才算加锁成功。它的假设是节点故障相互独立，但在实际部署中节点往往共享交换机、电源和运维通道，故障相关性很强；同时依赖各节点的时钟不发生大幅跳变。因此 Redlock 的安全性在社区一直有争议。

更稳妥的替代方案：对强一致要求高的场景使用 ZooKeeper 的临时顺序节点，或 etcd 的租约与事务；对只需要「尽量互斥、允许极小概率冲突」的场景，Redis 单实例加锁配合业务侧幂等即可。选型时要先明确冲突的业务代价，再决定锁的强度。
